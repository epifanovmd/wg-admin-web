# Project Conventions

Единые обязательные соглашения по написанию кода. Этот документ отвечает на вопрос
«как писать код» и не описывает конкретные модули приложения.

- Архитектурная модель, слои и границы: [ARCHITECTURE.md](ARCHITECTURE.md).
- Выбор слоя, слайса и сегмента: [FSD-CHEATSHEET.md](FSD-CHEATSHEET.md).
- Чистый код, SOLID и паттерны: [CLEAN-CODE.md](CLEAN-CODE.md) и
  [DESIGN-PRINCIPLES.md](DESIGN-PRINCIPLES.md).
- Если правило расходится с автоматически проверяемой конфигурацией, фактическое
  поведение определяется конфигурацией линтера, а расхождение устраняется отдельно.

## 1. Область действия

Правила распространяются на весь написанный вручную код приложения.

Не редактируются вручную:

- сгенерированный API-код;
- route tree и другие файлы, созданные router/codegen;
- сборочные артефакты.

Требования внешнего фреймворка или генератора имеют приоритет только для принадлежащих
ему файлов. Исключение должно быть локальным и задокументированным.

## 2. Именование директорий

Папки именуются в `kebab-case`:

```text
<domain-noun>/
<user-action>/
<technical-module>/
```

Имена слайсов описывают предметную область или пользовательское действие. Имена
сегментов описывают назначение кода.

Не создавать новые сегменты с именами:

```text
components/
hooks/
types/
utils/
```

Допустимые стандартные сегменты: `ui`, `model`, `api`, `lib`, `config`. Дополнительное
имя допустимо, если выражает устойчивую ответственность модуля.

Route groups, navigator groups и служебные каталоги фреймворка могут использовать
требуемое фреймворком имя.

## 3. Именование файлов

| Содержимое                      | Соглашение                            | Пример                             |
| ------------------------------- | ------------------------------------- | ---------------------------------- |
| React-компонент                 | `PascalCase.tsx`                      | `<Component>.tsx`                  |
| React-хук с основным экспортом  | имя файла совпадает с экспортом       | `use<Feature>VM.ts`                |
| Shared utility hook             | принятый в модуле `use-kebab-case.ts` | `use-latest-ref.ts`                |
| Обычный TypeScript-модуль       | `kebab-case.ts`                       | `<purpose>-<thing>.ts`             |
| Store в доменном слайсе         | `store.ts`                            | `entities/<entity>/model/store.ts` |
| Валидация                       | `validation.ts`                       | `model/validation.ts`              |
| Константы одного модуля         | `constants.ts`                        | `model/constants.ts`               |
| Типы всего небольшого сегмента  | `types.ts`                            | `model/types.ts`                   |
| Типы одного крупного компонента | `<name>.types.ts`                     | `<component>.types.ts`             |
| DI-регистрация                  | `<slice>.module.ts`                   | `<slice>.module.ts`                |
| Public API                      | `index.ts`                            | `<layer>/<slice>/index.ts`         |
| Dependency Inversion contract   | `<name>.contract.ts`                  | `<name>.contract.ts`               |

Имя не повторяет контекст без необходимости: внутри `entities/<entity>/model`
предпочтительно `store.ts`, а не `<entity>-store.ts`.

Если файл `.tsx` не экспортирует компонент, его имя всё равно должно описывать основной
экспорт. Не использовать JSX как причину складывать несвязанные декларации в один файл.

## 4. React-компоненты

В одном файле объявляется не более одного React-компонента.

Это относится к:

- экспортируемым компонентам;
- локальным helper-компонентам;
- компонентам внутри `memo` и `forwardRef`;
- render-компонентам compound API.

Обычные render-функции, возвращающие `ReactNode` для callback API, не становятся
отдельным компонентом, если не используются через JSX и не имеют собственного React
lifecycle.

Helper-компонент выносится в отдельный файл рядом с потребителем. Если он нужен только
одному компоненту, экспортировать его из public API не нужно.

`memo` применяется по измеримой причине или когда стабильность компонента является
частью существующего performance-контракта. Нельзя снимать мемоизацию только ради
прохождения структурного правила — реализацию и обёртку следует разделить корректно.

`forwardRef`-компоненту задаётся понятный display name, если инструменты не могут
вывести его автоматически.

## 5. Экспорты и public API

Корневой `index.ts` слайса формирует его внешний контракт и не содержит реализацию.

Правильно:

```ts
export { FeatureForm } from "./ui/FeatureForm";
export { useFeature } from "./model/useFeature";
export type { FeatureFormValues } from "./model/types";
```

Не использовать массовый `export *`, если он случайно раскрывает внутренние детали или
создаёт коллизии.

Public API экспортирует только то, что поддерживается для внешних потребителей.
Внутренние компоненты, store-классы и implementation details не экспортируются «на
всякий случай».

Deep import во внутреннюю структуру чужого слайса запрещён.

## 6. Импорты

- Между слоями и слайсами используются aliases.
- Внутри своего слайса или shared-модуля используются относительные пути.
- Импорт идёт через public API внешнего слайса.
- Импорты сортируются автоматически (`simple-import-sort`).
- Не создавать циклические зависимости через barrel-файлы.
- Type-only зависимости оформляются через `import type`, когда импорт не нужен в
  runtime.

Правильно:

```ts
import { IEntityStore } from "@entities/<entity>";
import type { FeatureFormValues } from "../model/types";
```

Неправильно:

```ts
import { IEntityStore } from "@entities/<entity>/model/types";
import { FeatureFormValues } from "@features/<feature>";
```

Второй пример является self-import, если расположен внутри `features/<feature>`.

## 7. Функции

- Все функции — стрелочные: `const fn = (a: A): B => {}`, `export const Component =
(props: IProps) => {}`, `const f = async <T,>(x: T) => {}` в `.tsx`. Объявления
  `function` и выражения `function` не используются — включая компоненты, хуки,
  хелперы модуля, type guards, фабрики и callback-и.
- Методы классов остаются методами.
- У `const` нет hoisting: хелпер объявляется выше первого использования.
- Хук, присваиваемый в свойство объекта, сначала объявляется именованной константой
  `useX`, чтобы правила хуков видели имя.
- Исключение — файлы деклараций типов и код, которым владеет фреймворк или генератор.

## 8. TypeScript и типы

- Не использовать `any`, если тип можно выразить безопасно.
- Не скрывать ошибку типов через необоснованные assertion и `as unknown as`.
- Тип располагается максимально близко к месту владения.
- Общий `shared/types` или сегмент `types` не создаётся.
- DTO находится рядом с API-контрактом; доменная модель — в `model`.
- Props компонента называются `I<Component>Props` или `<Component>Props` согласно уже
  принятому стилю модуля; внутри одного модуля стиль не смешивается.
- Публичные типы экспортируются явно через `export type`.
- Глобальные declaration augmentation используются только для действительно глобальных
  контрактов.

## 9. React-хуки

- Hooks вызываются только на верхнем уровне React-компонента или другого hook.
- Имя начинается с `use`.
- Dependency array отражает фактические зависимости и семантику эффекта.
- Нельзя механически менять dependency array только ради линтера, не проверив изменение
  поведения.
- Для стабильного callback, которому нужны свежие значения, используется принятый в
  проекте latest-ref/use-event паттерн.
- Mount-only effect должен быть действительно mount-only; причина стабильности
  зависимостей должна быть очевидна из структуры кода.
- Новые отключения `react-hooks/exhaustive-deps` не добавляются без отдельного
  обоснованного архитектурного решения.
  Такое решение — мемоизация колонок по отпечатку прав (раздел 10).
- Существующие точечные suppressions не расширяются и не считаются примером для нового
  кода.

Custom hook возвращает минимальный контракт. Навигация, UI и инфраструктура не
смешиваются с model-логикой без необходимости.

## 10. State и side effects

- Store хранит состояние и переходы, а не разметку.
- API и platform adapters находятся вне UI-компонента.
- Асинхронное состояние живёт в принятом механизме async-состояния, а не в ручной паре
  «локальный state + эффект-загрузка».
- Side effect запускается на уровне, который владеет его жизненным циклом.
- Глобальная инициализация, providers и composition находятся в `app`.
- Feature не выполняет навигацию, если результат сценария может быть сообщён
  callback/result и обработан page/app.
- Подписки, таймеры и listeners обязательно освобождаются.
- Асинхронный код учитывает cancellation или устаревший результат, когда это влияет на
  UI.

Права в UI:

- Доступ проверяется через стор текущего пользователя: право, его область или
  действие над конкретной сущностью по списку её владельцев. Строки прав не
  разбираются вручную в месте использования.
- Гейт и навигация — «хотя бы свои»; действие в строке или карточке — по этой
  сущности, а не по праву вообще.
- UI, зависящий от прав, мемоизируется по отпечатку прав. Колонки таблицы с
  действиями по строке — принятое исключение из полноты зависимостей: модель
  передаётся по стабильной ссылке, ключ мемоизации — отпечаток прав, причина
  указывается рядом с отключением.

## 11. Формы

- Форма описывается декларативно: схема валидации отдельно, компонент — только
  отображение и wiring.
- Валидация, общая для нескольких сценариев одного домена, живёт в соответствующей
  сущности, а не дублируется по features.
- Сообщения об ошибках принадлежат UI-слою, а правила — model-слою.

## 12. Стили и UI

- Используются принятые design tokens и UI-kit.
- Глобальные стили допустимы только в app-level styles.
- Компонент не добавляет произвольный глобальный CSS.
- Inline style допустим для действительно динамического значения; статическое оформление
  выносится в принятый механизм стилей.
- Статический стиль не пересоздаётся на каждом render.

## 13. Ошибки и результаты

- Ошибки не игнорируются молча.
- Пользовательское сообщение отделяется от технической ошибки.
- Истечение сессии и ошибки авторизации обрабатываются централизованно в auth/http
  lifecycle.
- Не показывать несколько одинаковых уведомлений из разных уровней одного запроса.
- Если проект использует result contract `{ data } | { error }`, новый код сохраняет
  этот контракт и не смешивает его с исключениями без отдельного решения.

## 14. Комментарии и документация

Комментарий объясняет причину, ограничение или неочевидный контракт, а не пересказывает
код.

Допустимы:

- краткий JSDoc публичного контракта;
- объяснение неочевидного performance/lifecycle решения;
- требование внешней библиотеки или платформы;
- обоснование локального исключения.

Не допускаются:

- история изменений;
- закомментированный старый код;
- очевидное описание следующей строки;
- комментарий, маскирующий неверное имя или слишком сложную функцию.

Документация проекта (`ARCHITECTURE.md`, `CONVENTIONS.md`, `FSD-CHEATSHEET.md`,
`CLEAN-CODE.md`, `DESIGN-PRINCIPLES.md`, `README.md`) не правится попутно с задачей.
Она меняется только в исключительных случаях — когда меняется архитектура, принцип
или паттерн проекта — и не содержит проектной конкретики. Если задача изменила
архитектурный факт или общее правило — об этом сообщается, а правка документа
выполняется отдельно.

## 15. Тесты

- Тест проверяет наблюдаемое поведение, а не внутреннюю реализацию.
- Исправление дефекта сопровождается regression test, если сценарий можно стабильно
  воспроизвести.
- Не использовать snapshot как единственную проверку важной бизнес-логики.
- Mocks располагаются рядом с тестом или в принятой тестовой инфраструктуре.
- Тесты не зависят от порядка запуска и очищают изменённое глобальное состояние.
- Сгенерированный код напрямую не тестируется; тестируется адаптер или потребитель.
- Модули с установленным порогом покрытия не изменяются без соответствующих тестов.
- Текущий пользователь в тестах подменяется общим фейком доступа с реальными
  правилами прав, а не объектом с одной функцией проверки: иначе тест не видит
  области «все / свои» и проверку по владельцам. Если права задаются после общей
  подготовки теста, фейк регистрируется как вычисляемое значение, а не константа.

## 16. ESLint и форматирование

- ESLint не отключается для файла или директории ради прохождения проверки.
- Новое локальное отключение правила допустимо только когда правило неприменимо
  технически, причина указана рядом, а более узкого решения нет.
- Autofix используется только после просмотра затрагиваемых файлов.
- Форматирование не смешивается с несвязанным функциональным изменением.
- Ошибки lint и typecheck исправляются в рамках задачи.
- Новое предупреждение считается незавершённой работой.

Часть соглашений проверяется автоматически, часть — только code review. Состав
автоматических проверок описан в [ARCHITECTURE.md](ARCHITECTURE.md).

## 17. Исключения

Исключение должно быть:

1. вызвано требованием framework/codegen/platform или подтверждённым техническим
   ограничением;
2. максимально узким;
3. задокументированным рядом с настройкой;
4. не расширяемым на новый код автоматически.

## 18. Проверка перед merge

Обязательный минимум — линтер, проверка типов, тесты и сборка. Git-хуки делят их:
на коммит — линтер и форматирование изменённых файлов, на push — проверка типов и
тесты; CI выполняет всё вместе со сборкой. Точные команды проекта перечислены в его
`README.md`.

```bash
<lint>        # линтер: 0 ошибок, включая границы слоёв
<typecheck>   # проверка типов без ошибок
<test>        # тесты, включая пороги покрытия
<build>       # сборка
git diff --check
```

## 19. Checklist

- [ ] Файл и директория названы по соглашению.
- [ ] В файле не больше одного React-компонента.
- [ ] Все функции стрелочные, хелперы объявлены выше использования.
- [ ] Типы находятся рядом с владельцем.
- [ ] Нет deep import и self-import через alias.
- [ ] Public API не раскрывает лишнюю реализацию.
- [ ] Dependency arrays не изменены механически.
- [ ] Нет новых необоснованных suppressions.
- [ ] Статические стили не создаются внутри render.
- [ ] Подписки и таймеры очищаются.
- [ ] Комментарии объясняют причину, а не код.
- [ ] Документация не изменена без явного запроса.
- [ ] Выполнены lint, typecheck, тесты и сборка.
